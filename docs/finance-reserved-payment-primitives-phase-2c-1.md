# Phase 2C-1: reserved payment accounting primitives

These synchronous, opt-in primitives are not an idempotent posting coordinator or a persistence acknowledgement. No production caller uses them. The shared runtime remains inactive and postingAllowed remains false.

## APIs

- Finance.addReservedDebtPayment(preparedReceipt): payment ID or null.
- Finance.addReservedLoanPayment(preparedReceipt): payment ID or null.
- Ledger.addReservedPaymentTransaction(preparedReceipt): transaction ID or null.

Each accepts the existing strict PaymentOperationReceipt type, requires prepared status and explicit reserved identifiers, and derives fields from its normalized immutable request. Account-funded receipts require a transaction reservation; custom loan receipts forbid one. No fallback ID is generated by these APIs. Collisions reject, including identical repeat insertions: replay is the future coordinator's responsibility.

Finance checks hydration, unique parent, currency/direction, account/category compatibility and reservation availability before calling the same private insertion functions as existing public actions. Those functions retain monetary rounding, overpayment, terminal-loan and principal-allocation validation. Reserved loan requests represent the existing simple repayment contract; legacy split payments remain supported by the unchanged public API.

Ledger verifies the exact saved payment against the receipt, rejects conflicting reservations/ownership, then uses the same dedicated payment validation and transaction creation functions as the public action. The account balance is affected only by the Ledger transaction. Fees are included in cash but not the installment amount. Custom-method payments never create a Ledger transaction.

Insertion does not attach a ledger ID or transition loan lifecycle/settlement: these remain separate Finance writes, preserving the future acknowledgement order. Existing linkage, lifecycle, edit and reversal behavior is retained. Public legacy wrappers discard extra JavaScript arguments, so their generated-ID behavior cannot accidentally select a reserved-ID path.

## Required Phase 2C-2 integration

Before invoking a primitive, the coordinator must own the shared accounting gate, await hydration and verified accounting recovery, check journal identity before parent/terminal checks, and durably acknowledge the prepared receipt. The receipt argument alone is not proof of journal acknowledgement. After each insertion it must await the corresponding tracked persistence barrier, attach linkage and apply lifecycle/settlement, verify exact ownership, then acknowledge completion. Never treat the synchronous returned ID as durable success.

On rejection or uncertainty after a partial write, retain reserved IDs and block for review; do not regenerate IDs or roll back entire arrays. Restart verification, completed/edited/reversed replay, journal tombstones and concurrency joining are not implemented here. These primitives do not prevent ID reuse after record deletion without the future journal coordinator. AsyncStorage writes across keys are not atomic and acknowledgements do not establish power-loss durability.
